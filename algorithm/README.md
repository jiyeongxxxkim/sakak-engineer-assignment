# 1. 알고리즘 문제: 개미 수열 (Look and Say Sequence)

## 1. 문제 이해

- 1번째 수는 `1`, 이후 수는 직전 수를 읽은 결과 (`1 → 11 → 21 → 1211 → 111221 ...`)
- 점화식이 없어 반드시 순차적으로 n번째까지 구해야 함
- 1번째를 제외한 모든 수는 `(개수, 숫자)` 쌍이라 길이가 짝수
- 중간수: n번째 수열의 길이를 `len`이라 할 때 `(len/2 - 1, len/2)` 위치의 두 수 (1번째 제외)

## 2. 풀이

- 직전 수를 순회하며 현재 숫자의 연속 개수를 카운트
- 숫자가 바뀌면 `개수 + 숫자`를 `StringBuilder`에 이어붙이고 카운터 초기화
- n번째까지 반복 후 중간 두 수 반환

## 3. TDD

- red → green 순서로 진행: 문제의 예시 값으로 테스트를 먼저 작성 후 구현
- refactor는 코드가 단순해 생략
- 예시는 모두 green, 하지만 더 큰 n에서도 통과할지는 미확인

## 4. 큰 n 직접 측정

n을 키워가며 직접 측정해 봄.

- n=50: 22ms / n=70: 약 1.1초 / n=78: 약 10.5초
- **n=80부터 `OutOfMemoryError`(힙 부족)

예시 테스트로는 알 수 없던 한계를 측정으로 확인.

## 5. 원인 분석: 복잡도

1. n마다 결과 문자열의 길이를 출력
2. 이웃한 항의 길이 비율 `L(n+1) / L(n)`은 n이 커질수록 약 1.30에 수렴 (n=45 근처 1.3036)
3. 항마다 길이가 약 1.3배씩 늘어 길이는 `O(1.3ⁿ)`
4. 각 단계는 직전 항을 한 번 훑으므로 시간은 길이에 비례, 단계 합은 등비급수라 마지막 항의 길이와 같은 차수
   → **시간 `O(1.3ⁿ)`**
5. 직전 항과 다음 항을 들고 있으므로 **공간 `O(1.3ⁿ)`**

→ 병목은 수열 전체를 메모리에 만드는 것. 지수적으로 늘어난 길이가 n=80에서 힙 한계를 넘음.

## 6. 개선 시도

#### 1.
**`String` → `byte[]`**
- `StringBuilder`가 이미 문자당 1바이트
- 지수 증가는 상수배 절감으로 해결되지 않음 → 적용 안함 

#### 2.
**필요한 구간만 계산**
- 중간 두 수가 이전 수열의 어느 블록에서 파생됐는지 알면 그 블록만 전개 가능
- 블록마다 길이 변화가 달라 추적 불가
    - `3 → 13` (2배 팽창)
    - `111 → 31` (오히려 감소)
- 더 진행하지 못함

## 7. 결과와 추가 학습

- 현재 풀이: n=78까지 동작, n=80부터 실패
- 제 풀이로는 해결하지 못했고, n=99 정도 보고 학습함
- 이 과정에서 개미 수열이 수학적으로 어떤 구조를 가지는지 알게 됨
- 앞으로도 막히는 문제는 한계를 확인하는 데서 끝내지 않고, 다른 접근을 찾아 학습할 예정
